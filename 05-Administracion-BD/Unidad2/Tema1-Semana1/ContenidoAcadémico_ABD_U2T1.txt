1.1. Estrategias de consistencia. 
La consistencia en una base de datos garantiza que, después de ejecutar 
una transacción, los datos se mantengan correctos y cumplan con las 
reglas definidas en el modelo y en las restricciones de integridad , las 
estrategias de consistencia se centran en aplicar controles que eviten 
anomalías, como registros duplicados o violaciones de claves foráneas, y 
en asegurar que toda transacción respete las propiedades ACID.  
 
 
De este modo, al finalizar cada operación, la base de datos pasa de un 
estado válido a otro igualmente válido, preserva la confiabilidad de la 
información almacenada  (Silberschatz et  al., 2020a , Armbrust et  al., 
2020). 
 
La consistencia es una de las propiedades esenciales de las 
transacciones dentro del modelo ACID, e sta asegura que cualquier 
transacción lleva a la base de datos de un estado válido a otro también 
válido, respeta las restricciones de integridad (claves primarias, foráneas, 
reglas de negocio) (Silberschatz et al., 2020).  
 
Las estrategias de consistencia implican: 
 
• Establecer reglas claras de integridad  cuando se diseña  el 
esquema. 
• Aplicar validaciones de forma automática, en el SGBD utilizando 
constraints y triggers. 
• Diseñar transacciones que cumplan con atomicidad y 
aislamiento, para evitar anomalías como actualizaciones 
perdidas o violaciones de integridad.

ACID, que rige el comportamiento de las transacciones en bases de 
datos, estas propiedades s on: Atomicidad, que asegura que una 
transacción se ejecuta en su totalidad o no se ejecuta; Consistencia, que 
garantiza que los cambios respeten todas las reglas de integridad, lleva

sí, como si se ejecutaran en serie; y Durabilidad, que asegura que una vez 
confirmada la transacción, sus efectos persisten incluso ante fallos del 
sistema. Así, las estrategias de c onsistencia no se entienden de manera 
aislada, sino como parte de un marco integral de control transaccional  
(Silberschatz et al., 2020).

1.2. Control de concurrencia.  
El control de concurrencia es el conjunto de técnicas y mecanismos que 
utilizan los sistemas de bases de datos para garantizar que múltiples 
transacciones que se ejecutan de manera simultánea no generen 
inconsistencias, en el caso que varios usuarios acceden y modifican datos 
al mismo tiempo, pueden producirse problemas como actualizaciones 
perdidas, lecturas sucias o resultados no repetibles. 
 
 
 
El objetivo del control de concurrencia es preservar la aislación de las 
transacciones (propiedad ACID), de  modo que el resultado final sea el 
mismo que si las transacciones se hubieran ejecutado en serie  (Zhao 
et al., 2022). 
 
Entre los métodos de control de concurrencia se encuentran: 
• Bloqueo (Locking):  Se emplean bloqueos compartidos en 
lectura y bloqueos exclusivos para escritura, para  evitar que dos 
transacciones modifiquen el mismo dato al mismo tiempo  
(Silberschatz et al., 2020). 
• Control por marcas de tiempo (Timestamp Ordering):  Cada 
transacción recibe una marca de tiempo y el sistema asegura 
que las operaciones se ejecuten en orden cronológico lógico  
(Silberschatz et al., 2020). 
• Control multiversión (MVCC):  Mantiene varias versiones de un 
dato para que las transacciones lean un estado consistente 
mientras otras escriben (Silberschatz et al., 2020). 
• Detección y prevención de deadlocks: El sistema debe  
identificar o evitar situaciones en las que varias transacciones 
esperen indefinidamente por recursos bloqueados entre sí  
(Silberschatz et al., 2020).

1.3. Copias de seguridad y tipos de respaldo.  
 
 
 
Copias de seguridad. 
 
Las copias de seguridad constituyen la primera línea de defensa frente a 
fallos, pérdidas de información o desastres , u na copia de seguridad 
consiste en duplicar total o parcialmente los datos almacenados en la 
base de datos para garantizar su disponibilidad en caso de error o daño, 
su propósito no es solo proteger la información, sino también asegurar la 
continuidad de las operaciones en las organizaciones , u n plan de 
respaldo bien diseñado permite reducir riesgos, optimizar tiempos de 
recuperación y ofrecer mayor confianza en la gestión de los datos  
(Thallapally, 2025). 
 
Tipos de copias de seguridad. 
 
Elegir una combinación eficaz de diferentes tipos de copias de seguridad 
puede afectar considerablemente el coste y la eficacia de su estrategia 
de protección de datos, ya que cada tipo de copia de seguridad tiene 
sus propias ventajas  y desventajas  (Thallapally, 2025) . Los tres tipos 
principales de copias de seguridad son: 
• Copia completa (Full Backup): Consiste en duplicar la totalidad 
de los datos de la base de datos , son fáciles de implementar y 
permiten restaurar el sistema en una sola operación. Sin 
embargo, requieren mayor tiempo de ejecución y un espacio 
de almacenamiento considerable. 
• Copia incremental (Incremental Backup):  Almacena solo los 
cambios realizados desde el último respaldo (sea completo o 
incremental), esto optimiza el us o de espacio y agiliza la 
ejecución del respaldo. El inconveniente es que la recuperación 
es más lenta, pues se necesita el último respaldo completo y 
todos los incrementales posteriores.

• Copia diferencial (Differential Backup):  Registra todos los 
cambios efectuados desde el último respaldo completo, ocupa 
más espacio que un respaldo incremental, su restauración es 
más rápida porque solo se necesita el último respaldo completo 
y el diferencial más reciente. 
 
Copias Físicas y Lógicas 
 
• Copias físicas:  Son copias que s e realiza  directamente de los 
todos los archivos binarios de la DB, como los ficheros de datos, 
logs de transacciones y metadatos , este método es eficiente y 
rápido, pero suele depender de herramientas específicas del 
sistema gestor. 
 
 
 Ejemplo:  
En PostgreSQL, usar pg_basebackup; en SQL Server, copiar 
archivos .mdf y .ldf dentro de un plan de respaldo. 
 
• Copias lógicas: Trabaja con las estructuras exportándolas como: 
tablas, esquemas, procedimientos y los datos en un formato 
legible, como scripts SQL, como ventaja p ermiten migrar datos 
entre versiones o sistemas distintos, aunque la restauración 
puede tardar más.  
 
 
 Ejemplo:  
En PostgreSQL, pg_dump y pg_dumpall; en SQL Server, el 
asistente de exportación de datos.

1.4. Planificación de respaldos y estrategias de recuperación. 
 
La planificación de respaldos y estrategias de recuperación son procesos 
organizacionales que define : qué respaldar, cuándo hacerlo y cómo 
recuperarlo en caso de fallo ; generar un respaldo no solo es ejecutar 
copias de seguridad; es necesario establecer po líticas claras que 
consideren aspectos como la frecuencia de respaldo, los recursos 
disponibles y los objetivos de la organización (Elmasri & Navathe, 2020).  
 
 
Una planificación  adecuada garantiza que los datos puedan 
recuperarse en el menor tiempo posible, reduc ir riesgos y tiempos de 
inactividad, también permite definir métricas como el RPO (Recovery 
Point Objective)  y el RTO (Recovery Time Objective) , que orientan las 
decisiones técnicas y estratégicas (Zgureanu, 2022). 
 
Elementos de un plan de respaldos y recuperación. 
 
El plan de recuperación constituye una herramienta primordial de las  
organizaciones tanto p úblicas como privadas, ya que garantizará la 
continuidad de las operaciones. Como elementos principales se 
consideran los siguientes:

• Frecuencia de respaldos: Define cada cuánto se deben realizar 
las copias de seguridad , puede variar desde minutos (en 
sistemas financieros críticos) hasta diarios o semanales en 
sistemas menos exigentes. Un buen diseño combina respaldos 
completos periódicos con diferenc iales o incrementales más 
frecuentes (Silberschatz et al., 2020). 
• Almacenamiento y retención:  Indica dónde se guardarán las 
copias (servidores locales, nube, cintas magnéticas, discos 
externos) y por cuánto tiempo se conservarán, esto depende de 
los recursos disponibles y de normativas legales que exijan 
mantener la información durante cierto periodo  (Silberschatz 
et al., 2020). 
• RPO (Recovery Point Objective):  Es la tolerancia máxima de 
pérdida de datos. Por ejemplo, si el RPO es de 4 horas, significa 
que se pueden perder como máximo las últimas 4 horas de 
trabajo, por lo que debe haber un respaldo al menos con esa 
periodicidad (Zgureanu, 2022). 
• RTO (Recovery Time Objective):  Representa el tiempo máximo 
permitido para recuperar el sistema tras una falla. Un RTO de 2 
horas significa que los respaldos y procesos de recuperación 
deben estar diseñados para restablecer la operación en menos 
de ese tiempo (Zgureanu, 2022). 
• Pruebas de recuperación:  No basta con generar copias; se 
debe comprobar periódicamente que las restauraciones 
funcionan correctamente , m uchas organizaciones descubren 
que sus respaldos son inútiles porque nunca probaron el proceso 
de recuperación (Silberschatz et al., 2020). 
• Automatización y monitoreo: Los SGBD modernos y herramientas 
externas permiten programar respaldos automáticos y generar 
alertas en caso de fallos. Automatizar evita olvidos humanos y 
monitorear asegura que siempre se cumpla el plan definido  
(Silberschatz et al., 2020).

pueda restaurar la base de datos en menos de 2 horas  y con una 
pérdida máxima de datos de 30 minutos, garantiza la cont inuidad 
del negocio y la confianza de los clientes.

DECLARE  
    @DBName        sysname      = 
N'Empresa',                          -- Nombre de la base a respaldar 
    @BackupPath    nvarchar(260) = 
N'C:\Respaldos\Empresa_Full.bak',   -- Ruta completa del archivo .bak

   1) LIMPIEZA: Si ya existe un Job con el mismo nombre, eliminarlo 
   ------------------------------------------------------------ */ 
IF EXISTS (SELECT 1 FROM msdb.dbo.sysjobs WHERE name = @JobName) 
BEGIN 
    EXEC msdb.dbo.sp_delete_job @job_name = @JobName; 
END 
GO

   2) CREAR EL JOB 
   ------------------------------------------------------------ */ 
EXEC msdb.dbo.sp_add_job   
     @job_name   = N'Respaldo_Completo_Empresa', 
     @enabled    = 1, 
     @description= @Description; 
GO

/* ------------------------------------------------------------ 
   3) AGREGAR PASO (BACKUP FULL) 
   - WITH INIT sobrescribe el archivo .bak; quítalo si deseas 
acumular historiales 
   ------------------------------------------------------------ */ 
DECLARE  
    @CmdBackup nvarchar(max) =  
N'BACKUP DATABASE ' + QUOTENAME(N'Empresa') + N' 
 TO DISK = ''' + N'C:\Respaldos\Empresa_Full.bak' + N''' 
 WITH INIT,  
      NAME = ''Respaldo completo Empresa'', 
      CHECKSUM, STATS = 10;'; 
 
EXEC msdb.dbo.sp_add_jobstep 
     @job_name      = N'Respaldo_Completo_Empresa', 
     @step_name     = N'Ejecutar_Backup_Full', 
     @subsystem     = N'TSQL', 
     @database_name = N'master',              -- El BACKUP no 
requiere contexto en la BD usuario 
     @command       = @CmdBackup, 
     @on_success_action = 1,                  -- Quit 
     @on_fail_action    = 2;                  -- Quit with failure 
GO 
 
/* ------------------------------------------------------------ 
   4) CREAR HORARIO (domingo 2:00 AM) 
   - @freq_type = 8 => semanal 
   - @freq_interval = 1 => domingo (bitmask: 1=Dom, 2=Lun, 4=Mar, 
8=Mié, 16=Jue, 32=Vie, 64=Sáb) 
   - @active_start_time en formato HHMMSS 
   ------------------------------------------------------------ */ 
EXEC msdb.dbo.sp_add_schedule 
     @schedule_name    = N'Horario_Semanal_Domingo_2AM', 
     @freq_type        = 8, 
     @freq_interval    = 1, 
     @active_start_time= 020000; 
GO 
 
/* ------------------------------------------------------------ 
   5) ASOCIAR EL HORARIO AL JOB 
   ------------------------------------------------------------ */ 
EXEC msdb.dbo.sp_attach_schedule 
     @job_name      = N'Respaldo_Completo_Empresa', 
     @schedule_name = N'Horario_Semanal_Domingo_2AM'; 
GO

/* ------------------------------------------------------------ 
   8) VERIFICAR RESULTADOS (historial del job) 
   - Revisa también en SSMS: SQL Server Agent > Jobs > Job History 
   ------------------------------------------------------------ */ 
SELECT TOP (20) 
       j.name              AS JobName, 
       h.step_id, 
       h.step_name, 
       h.run_date, 
       h.run_time, 
       h.run_duration, 
       h.sql_message_id, 
       h.sql_severity, 
       h.message 
FROM   msdb.dbo.sysjobhistory AS h 
JOIN   msdb.dbo.sysjobs       AS j ON h.job_id = j.job_id 
WHERE  j.name = N'Respaldo_Completo_Empresa' 
ORDER BY h.instance_id DESC; 
GO
